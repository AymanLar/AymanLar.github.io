## Context

I have always been someone who loves music — both listening to it and making it, even when the outcome is questionable. What I enjoy most is the process: plugging in an unplugged electric guitar, routing it through a soundcard, opening a DAW, stacking tracks, and mixing. That said, this post is not about making music. It is about discovering it.

Last.fm has long been my go-to service for music discovery. Its "library", "mix", and "recommended" stations surface an endless stream of artists I would never have found on my own. The problem is that I do not have Last.fm Premium, which is what would let me sync those discoveries directly into Spotify — the service I actually use to listen. Recreating those stations as playlists by hand was tedious, so I did what any developer would do: I wrote a small Python script to do it for me.

The script worked, but it only worked for me. `lastlist` is the web version of that script — a small application that makes the same workflow available to anyone.

![lastlist homepage](/assets/lastlist.png)

## The Idea

The concept is deliberately simple: give the app a Last.fm username and a station type, and it produces a Spotify playlist in your account containing the tracks from that station.

Because Last.fm listening histories are public by default, this also opens up a few interesting uses beyond your own account:

- **Personal playlists** — turn your own Last.fm mix or recommendations into something you can play on Spotify.
- **Playlists for friends** — enter a friend's username and build a playlist that reflects their taste. It makes for a genuinely thoughtful surprise.
- **Music discovery** — explore an artist's or a friend's listening profile and find new music through their history.

## Architecture

`lastlist` is intentionally minimal. It is a single-process Flask application with server-rendered Jinja2 templates and no database.

| Layer | Technology |
|---|---|
| Language | Python 3 |
| Web framework | Flask + Jinja2 |
| Spotify integration | `spotipy` with `SpotifyOAuth` |
| HTTP client | `requests` |
| Configuration | `python-dotenv` |
| Deployment | Vercel (`@vercel/python`) or any WSGI host |

The entire application lives in one file (`app.py`), supported by three templates (`index.html`, `lastfm.html`, `playlist.html`) and a single stylesheet. There is no persistence layer: all state that needs to survive a redirect — the Spotify token, the Last.fm username, and the selected station type — lives in Flask's signed client-side session, stored under a custom cookie name (`spotify-login-session`).

That design makes the app completely stateless on the server, which in turn makes deployment trivial. `vercel.json` maps every incoming path to `app.py` through a catch-all route, and the same four environment variables work locally and in production.

## How It Works

The request flow follows the OAuth 2.0 authorization-code pattern:

1. `/` renders the landing page.
2. `/login` redirects the user to Spotify's consent screen via `sp_oauth.get_authorize_url()`. The requested scope is `playlist-modify-public`.
3. `/callback` receives the authorization code, exchanges it for an access token with `get_access_token(code)`, stores it in the session, and redirects to the form.
4. `/lastfm_user` shows the input form; posting to `/lastfm` saves the username and station type in the session.
5. `/playlist` runs the actual conversion.

The conversion itself has three steps. First, it fetches the station from Last.fm by calling the station endpoint:

```
https://www.last.fm/player/station/user/{username}/{type}/
```

The JSON response contains a `playlist` array, and the app extracts each track's name and first artist. This is an internal Last.fm endpoint rather than the documented REST API — which means it needs no API key, but also means it is not a stable public contract and could change without notice.

Next, it creates a public playlist in the authenticated user's account, named `{username}'s {type} Tracks`. Finally, for every track it queries Spotify:

```
q = "track:{track_name} artist:{artist_name}"
```

The first search result is taken as a match and its URI is collected. All matched URIs are added to the playlist in a single batch call. The confirmation page then lists the tracks that were picked up from Last.fm.

Everything runs synchronously inside the `/playlist` request, so the wait time grows linearly with the number of tracks — two external services are called sequentially, with one Spotify search per track. There is no queue, cache, or background worker; for a tool of this size, the simplicity is a feature.

## Getting Started

To run it locally:

```bash
git clone https://github.com/AymanLar/lastlist.git
cd lastlist
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Copy `.env_empty` to `.env` and fill in the four values:

```env
SPOTIPY_CLIENT_ID=your_client_id
SPOTIPY_CLIENT_SECRET=your_client_secret
SPOTIPY_REDIRECT_URI=http://127.0.0.1:5000/callback
FLASK_SECRET_KEY=a_long_random_secret
```

The first two come from the [Spotify Developer Dashboard](https://developer.spotify.com/dashboard), where the redirect URI must also be registered. No Last.fm credentials are needed — the username is entered in the web form at runtime.

Then start the app:

```bash
python app.py
```

Open `http://127.0.0.1:5000`, log in with Spotify, enter a Last.fm username, choose a station type, and submit. The new playlist appears in your Spotify account.

For production, import the repository into Vercel and set the same environment variables there. Remember to change `SPOTIPY_REDIRECT_URI` to your deployed `/callback` URL and register that URL with Spotify. `gunicorn` is included in the dependencies if you would rather self-host behind a traditional WSGI server.

## Reflections

`lastlist` began as a personal workaround and became a small exercise in shipping something useful with very little machinery. Its architecture — one Flask file, a signed cookie, and two third-party APIs — is deliberately modest, and that is what allowed me to go from script to deployed web app in a few days.

There are obvious improvements if I revisit it: token refresh instead of forcing a re-login, better track matching than "first search result wins", error handling around the undocumented Last.fm endpoint, and moving the per-track searches into a background job for large playlists. But those are refinements, not blockers. The core idea works, and the app has been quietly doing its job since 2024.

Have fun with it.
