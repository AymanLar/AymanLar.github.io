## Context

Streaming services are convenient, but they are not the only way to listen to music. My local library — a folder of carefully named MP3s, FLACs, and other files — is fed into [MPD](https://www.musicpd.org/), the Music Player Daemon. MPD is excellent at playing local files, but it has one fundamental limitation: it can only play what is in its own database. A Spotify playlist, on the other hand, lives entirely in the cloud.

`s2mpdpl` — **S**potify **2** **MPD** **PL**aylist — is a command-line tool that bridges that gap. Give it a Spotify playlist URL and the path to your local music library, and it produces an M3U playlist that MPD can load, with each Spotify track resolved to a matching file on disk.

The name is not subtle, but it is accurate: this is a converter, not a sync service. Spotify decides *what* should be in the playlist; the tool figures out *where* those tracks live locally.

## Architecture

The project is a small Python CLI with four modules and a thin entry-point script. There is no web framework, no database, and no packaging layer — just standard-library tooling plus a few focused dependencies.

| Layer | Technology |
|---|---|
| Language | Python 3 |
| Spotify API | `spotipy` with `SpotifyClientCredentials` |
| Configuration | `python-dotenv`, plain `Config` class |
| Fuzzy matching | `fuzzywuzzy` + `python-Levenshtein` |
| Output | M3U plaintext (UTF-8) |
| Entry point | `convert.py` (argparse via `src/main.py`) |

The module layout is straightforward:

```
convert.py           CLI wrapper that adds src/ to sys.path
src/config.py        environment-driven Config class + validate()
src/fetch.py         Spotify API → playlist.txt
src/mapper.py        playlist.txt + local files → .m3u
src/main.py          orchestration and CLI arguments
```

Dependencies flow one way: `main.py` imports `fetch`, `mapper`, and `config`; both `fetch` and `mapper` depend on `config`. The wrapper exists because `src/` has no `__init__.py`, so its modules are imported as top-level modules after a small `sys.path` adjustment.

## How It Works

The pipeline has two distinct stages that communicate through a file on disk.

### 1. Fetching from Spotify

`fetch.py` authenticates with the **Client Credentials** OAuth flow. This is an app-level token with no browser redirect and no user context — fast and simple for a CLI, but with an important consequence: only public playlists are accessible. Private playlists require an authorization-code flow with a user token, which the earlier version of the tool actually used before I simplified it.

The playlist ID is extracted from the last segment of the URL, and `sp.playlist_tracks()` is called with a pagination loop, since Spotify returns at most 100 items per page. The resulting tracks are written to `playlist.txt` as lines of the form:

```
Track Name — Artist One, Artist Two
```

### 2. Mapping to local files

`mapper.py` reads that intermediate file and, for each track, scans the music directory recursively for files with a supported extension (`.mp3`, `.flac`, `.m4a`, `.ogg`, `.wav`, `.aac`). Filenames are normalized by lowercasing, stripping punctuation, and collapsing whitespace, then compared with `fuzz.ratio` — a Levenshtein-based similarity score from 0 to 100. The best candidate above a strict threshold of 70 wins.

The matched file's absolute path is then rewritten relative to the music root, with forward slashes:

```python
os.path.relpath(file_path, music_dir).replace(os.sep, '/')
```

MPD expects paths relative to its music directory, and forward slashes keep the output portable even when the tool runs on Windows. A `ValueError` fallback handles cross-drive situations where a relative path cannot be computed.

Finally, the relative paths are written one per line to `<name>.m3u`. If `MPD_PLAYLIST_DIR` points to an existing directory, the file is copied there automatically; otherwise it stays in the working directory for manual copying.

The trade-off in this design is matching quality versus complexity. Only filenames are compared — no ID3 tags, album names, or durations — and the entire library is walked once per track. That is fine for a few hundred songs, but it means the algorithm is O(tracks × files) and a large library will make you wait.

## Getting Started

Install the dependencies and configure the environment:

```bash
pip install -r requirements.txt
cp env.example .env
```

Edit `.env` with your Spotify app credentials from the [Developer Dashboard](https://developer.spotify.com/dashboard) and the path to your library:

```env
SPOTIFY_CLIENT_ID=your_client_id
SPOTIFY_CLIENT_SECRET=your_client_secret
MUSIC_DIRECTORY=/home/user/Music
OUTPUT_PLAYLIST_NAME=spotify_playlist
MPD_PLAYLIST_DIR=/home/user/.mpd/playlists/
```

Then convert a playlist:

```bash
python convert.py "https://open.spotify.com/playlist/your_playlist_id"
```

You can override the output name and library path per invocation:

```bash
python convert.py "playlist_url" --output "roadtrip" --music-dir "/mnt/music"
```

Once the `.m3u` is in MPD's playlist directory, load it with `mpc`:

```bash
mpc load spotify_playlist
mpc play
```

## Reflections

`s2mpdpl` is a good example of a tool that does one thing without ceremony. The two-stage design — fetch to a text file, then map to M3U — means each half can be run independently for debugging. The fuzzy-matching step is simple enough to understand in one sitting, yet good enough to recover most tracks from a library that does not follow Spotify's naming conventions.

Looking forward, the improvements I would consider are building an in-memory filename index to avoid repeated directory walks, using audio metadata for better matches, restoring user-token authentication for private playlists, and replacing print statements with structured logging. For now, it solves the problem it was written for: getting a Spotify playlist into MPD without clicking through hundreds of files.
